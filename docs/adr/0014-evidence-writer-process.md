# ADR 0014 — The evidence writer is its own process with its own file

**Status:** accepted · **Date:** 2026-11-12

**Context.** Invariant 5 (SR-04): only the evidence writer has code that writes `evidence.db`,
and it is a separate process from the first build. Until now the backend queued evidence events
in its outbox and nothing consumed them ("events stay pending"). The writer also had to support
signed checkpoints, signed exports that an auditor can check with `apps/verifier-cli`, and a
restore on a new device that continues the chain without hiding a fork (MVP 9.2, AC-13, AC-17,
AC-18).

**Decision.**
- **Package and process.** `services/evidence-writer` (`aios_evidence_writer`) is a separate
  Python package and a separate PyInstaller executable (`evidence-writer.exe`, its own spec in
  `build/pyinstaller/`). The backend starts it as a child in its Job Object, so it ends with the
  backend. The import-linter contracts forbid the backend from importing the writer and the
  writer from importing the backend or `db`.
- **Authentication** follows Process and IPC v1. The backend sends a handshake frame on stdin
  with the derived token `derive(T, "aios/ipc/v1/evidence-writer")`; the writer answers
  `READY {"api_port":N}` and serves FastAPI on loopback only, behind the token middleware. The
  launch token itself never reaches the writer.
- **Storage.** `evidence.db` is plain SQLite opened with `locking_mode=EXCLUSIVE` and WAL, so a
  second writer on the same file fails (`WriterLocked`, exit code 3). It is not encrypted: it
  holds content-free bodies (ids, classifications, digests, counts; commitment nonces stay in
  `chats.db`), and an auditor must be able to read an export without AIOS keys.
- **Delivery.** The backend's outbox pump sends pending events in order. `intent_id` = the
  outbox `event_id` and is unique in the writer, so a resend after a crash is a no-op. The
  writer assigns `seq`, `prev_hash` and `event_hash` and reports them back; the backend only
  mirrors them for the UI.
- **Signing.** Ed25519 checkpoints every 100 events, after 5 minutes, on export, on shutdown and
  over every continuation. The seed lives in the keystore (`evidence-signing-seed`) and in the
  Recovery Package; never in files or logs.
- **Restore rotates the key.** A restore opens a new epoch with a new key. The old key signs a
  handover checkpoint over the `continuation` event, then the new key signs one. A second device
  still writing with the old key therefore shows up as `branched` in the verifier instead of
  passing silently.
- **Exports** are a ZIP of four entries (`manifest.json`, `manifest.sig.json`, `events.jsonl`,
  `checkpoints.jsonl`) with fixed timestamps. The writer builds and signs them; the backend
  writes the file where the user chose and records `evidence_exported`.

**Consequences.**
- One more executable to sign and ship (`release.yml` signs `build/out/evidence-writer`).
- `evidence_writer` is a health component: while the writer is down, events stay pending in the
  outbox and are delivered when it is back. Nothing is lost, and the UI says so.
- The backend never names `evidence.db`; it asks the writer for its file name (a guard test
  keeps the literal out of the backend).
- The wire format is in `contracts/evidence-wire-format/v1`; golden vectors generated by
  `tools/contracts/gen_evidence_vectors.py` are checked in CI against both the writer and the
  TypeScript verifier.
